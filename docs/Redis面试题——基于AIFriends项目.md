# Redis 面试题 —— 基于 AIFriends 项目

> AIFriends 是一个 AI 面经社区（Django + MySQL + Redis），Redis 作为缓存层部署在本地 Docker（端口 16379）和生产服务器（端口 6379），缓存首页笔记列表、笔记详情、用户统计、评论列表等热点数据。

---

## 1. Redis 是什么？简述它的优缺点？

**是什么**：Redis（Remote Dictionary Server）是一个基于内存的键值存储数据库，数据存在内存中，读写极快。支持多种数据结构（String、Hash、List、Set、Sorted Set 等），常用于缓存、会话存储、消息队列等场景。

**在我的项目中的作用**：存放"短时间内不太会变，但访问量很大"的数据。比如首页面经列表，每个用户打开网站都要请求一次，如果每次都去 MySQL 里 JOIN 几张表、聚合点赞/收藏/评论数，查询量大时数据库扛不住。Redis 在中间挡一层，MySQL 的数据查一次就放 Redis 里，后面 2 分钟内的请求直接从 Redis 返回，MySQL 不用重复干活。

**优点**：
- **极快**：数据在内存，单机 QPS 可达 10 万+
- **数据结构丰富**：不只是 String，还有 Hash、List、Set、Sorted Set，能应对各种场景
- **持久化**：RDB 快照 + AOF 日志两种方式把内存数据刷到磁盘，重启后数据还在
- **简单**：单个 `redis-server` 进程，部署维护成本低

**缺点**：
- **内存贵**：数据量受内存大小限制，不能像 MySQL 那样存 TB 级数据
- **可靠性问题**：异步刷盘可能导致宕机时丢失最近几秒的数据（项目里设置了 2-5 分钟的 TTL，丢就丢了，查一次 MySQL 又补回来）
- **单线程**：一个 Redis 实例只用一个线程处理命令（6.0+ 引入多线程 IO 但核心执行仍是单线程），CPU 密集操作会阻塞

---

## 2. Redis 为什么这么快？

**五个原因**：

1. **纯内存操作**：绝大部分时间花在内存读写上，不碰磁盘。内存纳秒级，磁盘毫秒级，差 6 个数量级
2. **单线程 + 事件驱动**：不用加锁、不用上下文切换，数据竞争和死锁天然不存在。一个线程专心处理命令，省去了大量 CPU 开销
3. **IO 多路复用**：一个线程同时监听多个 socket，哪个有数据到了就处理哪个，单线程也能撑起几万连接（详见第 15 题）
4. **高效的数据结构**：不是用高级语言自带的 HashMap，而是自己实现压缩链表、跳表等，更省内存更快
5. **RESP 协议简洁**：Redis 的通信协议是纯文本的，解析极快，不需要复杂的序列化

---

## 3. 为什么要用 Redis 做缓存？

**核心问题**：数据库是瓶颈。MySQL 数据在磁盘，每次查询要读磁盘，再加上 JOIN、聚合等操作，单次查询可能几十毫秒。1000 个用户同时刷首页，MySQL 可能就扛不住了。

**Redis 解决什么**：
- **减少数据库压力**：热点数据暂时在 Redis，95% 的请求走 Redis，MySQL 只处理 5%
- **降低延迟**：MySQL 查一次可能要 10-50ms，Redis 不到 1ms
- **高并发支撑**：项目选了 Django+Gunicorn，Gunicorn 只有 3 个 worker，如果不缓存，每个 worker 处理一个请求就要去查 MySQL，3 个请求就能堵住。加上 Redis 后，worker 直接拿缓存返回，吞吐量大幅提升

**在我的项目中**：`benchmark.py` 实测首页列表从 9-13 次数据库查询降到缓存命中时 0 次。

## 4. Redis 与 MySQL 的区别？

| 维度 | Redis | MySQL |
|------|-------|-------|
| **存储位置** | 内存 | 磁盘 |
| **速度** | 纳秒~微秒级 | 毫秒级 |
| **数据模型** | KV + 多种数据结构 | 关系型，表/行/列 |
| **查询能力** | 只能按 Key 查 | SQL，支持复杂查询 |
| **持久化** | 可选用 RDB/AOF | 默认持久 |
| **容量** | 受内存限制（GB 级） | 可达 TB 级 |
| **一致性** | 最终一致性 | ACID 事务 |
| **角色** | 缓存层 | 数据源 |

**在项目中的分工**：
- **MySQL**：数据的"家"，所有面经、用户、评论的真正存储位置
- **Redis**：数据的"前台"，把热点数据提前准备好放内存，用户来了直接从 Redis 拿，省去查 MySQL 的时间

两者不是替代关系，是配合关系 — MySQL 做持久化存储，Redis 做性能加速。

## 6. 每种数据类型对应的底层数据结构？

| 数据类型 | 底层实现 | 为什么这样设计 |
|---------|---------|--------------|
| **String** | SDS（Simple Dynamic String） | C 字符串不安全（缓冲区溢出），SDS 记录了长度和空闲空间，追加时直接扩容，不会溢出。还存了 `len` 属性，O(1) 获取长度 |
| **Hash** | 数据少时用 ziplist（压缩列表），数据多时用 hashtable（哈希表） | ziplist 连续内存，无指针，省内存。数据多了转 hashtable 保证 O(1) 查询 |
| **List** | 3.2 之前用 linkedlist + ziplist，3.2+ 用 quicklist | quicklist 是 linkedlist 的每个节点放一个 ziplist，兼顾了链表的插入效率和压缩列表的存储密度 |
| **Set** | 数据少时用 intset（整数集合），多时用 hashtable | intset 去重 + 有序，整数场景比 hashtable 省内存 |
| **Sorted Set** | 数据少时用 ziplist，多时用 skiplist（跳表）+ hashtable | 跳表支持范围查询（ZRANGE），hashtable 支持 O(1) 按 key 查分数，双结构配合 |

## 7. 持久化的三种方法？

**1. RDB（Redis Database）**

定时把内存数据拍快照存到磁盘（`.rdb` 文件）。

优点：文件紧凑，恢复快。缺点：两次快照之间的数据如果宕机会丢失。

**2. AOF（Append Only File）**

把每条写命令追加到日志文件，重启时重放一次命令恢复数据。

优点：丢数据少（可以配置每条命令都刷盘或每秒刷一次）。缺点：文件大，恢复慢。

**3. 混合持久化（RDB + AOF，Redis 4.0+）**

AOF 重写时先拍 RDB 快照，再把快照之后的增量命令追加到后面。恢复时先加载快照再重放增量命令。

**在我的项目中**：没有开启持久化。缓存数据有 TTL（2-5 分钟），就算 Redis 重启缓存清空，第一次请求会从 MySQL 重新查，后续请求又回到缓存轨道。对业务零影响。

## 8. Redis 如何实现分布式锁？

用 `SET key value NX EX 30` 一条命令搞定：
- `NX`：Not eXists，只有当 key 不存在时才设置成功（获取锁）
- `EX 30`：30 秒自动过期（防止持有锁的进程崩溃导致死锁）

释放锁时不能直接 `DEL`，因为可能锁已经过期被其他进程获取了。要用 Lua 脚本原子性检查 value 是否匹配再删除：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

**在我的项目中**：暂时没用分布式锁（单机部署），但如果有多个 worker 同时操作同一份缓存数据，可以用这种方式保证互斥。

## 9. 哨兵机制？

Sentinel（哨兵）是 Redis 的高可用方案，处理主从架构下主节点挂掉的问题。

**三个任务**：
1. **监控**：定期 PING 主节点和从节点，看谁还活着
2. **通知**：某个节点挂了，发消息通知管理员或客户端
3. **自动故障转移**：主节点下线后，从剩下的从节点里投票选一个新的主节点，然后把所有从节点指向新主节点

**在我的项目中**：单机 Redis，主从 + 哨兵都没部署。如果生产环境要上高可用，可以配置一主两从 + 三个哨兵，但当前数据量和流量不需要。

## 10. 过期删除？

Redis 用两种策略组合：

**惰性删除**：key 过期后不立刻删除，等到有请求来访问这个 key 时再检查，过期了就删掉返回空。省 CPU，但占用内存。

**定期删除**：每隔 100ms 随机抽 20 个 key 检查，过期了删掉。如果这 20 个里有过期比例超过 25%，就再抽 20 个继续删。控制每次执行时间不超过 25ms，避免卡住。

两者配合：惰性删除兜底（保正过期的 key 不会被返回），定期删除清场（防止内存占满）。

**在我的项目中**：缓存 key 设置了 `timeout` 参数（120-300 秒），时间一到就依赖 Redis 的过期机制自动清理。不需要手动 `EXPIRE`。

## 11. LRU 算法和 LFU 算法？

当内存满了，再写入新数据时，Redis 需要淘汰旧数据腾出空间：

**LRU（Least Recently Used，最近最少使用）**：最近被访问过的留着，最久没被访问过的淘汰。假设"最近用过 → 以后可能还会用"。

- 近似实现：采样 N 个 key，踢掉其中空闲时间最长的那个（不是严格全局 LRU，但性能好很多）
- 缺点：一个冷门 key 偶尔被扫一次就会赖着不走

**LFU（Least Frequently Used，最少频率使用）**：访问次数最少的淘汰。假设"以前用得多 → 以后还用得多"。

- Redis 4.0 引入，额外记录访问频率计数器
- 适合热点数据明显的场景

**在我的项目中**：都没用。项目走的是 **TTL 淘汰**，每个缓存 key 都设置了 2-5 分钟的过期时间，过期后自动删除。内存没满的情况下不需要 LRU/LFU。但如果未来缓存数据量暴增，可以配置 `maxmemory-policy allkeys-lru` 或 `allkeys-lfu` 作为保底。

## 12. 如何保证数据库和缓存的一致性？

这是缓存使用的核心难题。两种常见策略：

**策略一：Cache Aside（旁路缓存，我的项目用的就是这个）**

```
读：先查 Redis → 有就返回 → 没有就查 MySQL → 写回 Redis
写：先更新 MySQL → 再删除 Redis 缓存
```

**为什么是删除缓存而不是更新缓存？** 如果两个写请求并发，可能出现"后更新的 DB 数据被先更新的缓存覆盖"的问题。直接删了，下次读再查 DB，安全。

**为什么先更新 DB 再删缓存？** 反过来（先删缓存再更新 DB）会有问题：删了缓存后、DB 还没来得及更新前，另一个读请求进来查到旧数据写回缓存，缓存就脏了。

**策略二：延迟双删**：先删缓存 → 更新 DB → 等一会（500ms）再删一次缓存，进一步降低脏数据概率。

**在我的项目中的实现**：

在 `cache.py` 里，每次写操作都会触发缓存失效：

```python
# 比如点赞操作后（toggle_like.py）
invalidate_note(note_id)        # 删除单个笔记缓存
invalidate_user_stats(user_id)  # 删除用户统计缓存

# 比如创建新笔记后
invalidate_note_list()          # 删除所有首页列表缓存
invalidate_user_stats(user_id)
```

关键是"删缓存"而不是"更新缓存"，保证了下一次读请求会从 MySQL 拿最新数据再写回 Redis，不会出现数据不一致。

**如果极端情况下还是不一致了怎么办？** 项目里的 TTL 只有 2-5 分钟，最多 5 分钟后就自动恢复了。这叫"最终一致性"，比"强一致性"代价低得多，对社区类应用完全够用。

## 13. 缓存穿透？

**是什么**：查询一个不存在的数据（比如 `note_id = -1`），缓存里没有，MySQL 里也没有。每次请求都穿过了缓存打到数据库。如果恶意攻击者用不存在的数据大量请求，能打穿 MySQL。

**解决方案**：
1. **布隆过滤器**：在缓存前面再加一层，用很小的内存判断"这个 key 绝对不存在"，不存在的直接返回，不查 MySQL
2. **缓存空对象**：查 MySQL 发现数据不存在时，也在 Redis 写个空标记（TTL 设短一点，比如 1 分钟）

**在我的项目中**：这个风险较低，因为 `get_list` 的查询不会打到"不存在的 note_id"，`search_query` 也只是模糊匹配，不会特意用不存在的 ID 攻击。但如果未来要做按 ID 查询的接口，加一层布隆过滤器是最优解。

## 14. 缓存击穿？

**是什么**：一个热点 key（比如最热的那篇面经的详情页），在过期瞬间刚好有大量并发请求过来，这些请求全部绕过缓存去查 MySQL，数据库瞬间被压死。

**和穿透的区别**：穿透是数据不存在，击穿是数据存在但缓存刚好过期了。

**解决方案**：
1. **互斥锁**：第一个请求发现缓存过期后，获取锁然后去查 DB 更新缓存，后面的请求等着，等缓存更新好了再从缓存拿
2. **永不过期**：对真正超级热点数据不设 TTL，改成异步更新
3. **逻辑过期**：缓存里不设 TTL 而是存一个逻辑过期时间，定时任务提前刷新

**在我的项目中**：没做特殊处理，因为单个面经详情页的并发量不会太高，TTL 5 分钟，即使"击穿"了一次，MySQL 也扛得住。但如果未来上了一篇爆款面经大量用户同时涌入，可以考虑加互斥锁。

## 15. 缓存雪崩？

**是什么**：大量缓存 key 同时过期（或者在同一个时间点 Redis 挂了），所有请求都瞬间砸到 MySQL，数据库直接崩掉。

**和击穿的区别**：击穿是单个热点 key，雪崩是大量 key 同时失效。

**解决方案**：
1. **加随机值打散 TTL**：不要所有 key 都用 300 秒，改成 `300 + random(0,60)` 秒，避免同时过期
2. **多级缓存**：本地缓存 + Redis 缓存，Redis 挂了还有本地兜底
3. **熔断/限流**：后端 MySQL 扛不住的时候直接返回友好提示，保护数据库
4. **高可用**：Redis 主从 + 哨兵，主节点挂了从节点顶上来

**在我的项目中**：
- 列表和详情的 TTL 不一样（120s vs 300s），不会同时过期，天然错开
- 用了 `LocMemCache` 做降级：如果 Redis 连接失败，Django 的配置会回退到本地内存缓存，虽然各 worker 之间不共享，但至少不会打崩 MySQL

## 16. Redis 事务？

Redis 事务用 `MULTI` / `EXEC` / `WATCH` 实现：
- `MULTI` 开启事务，之后的命令会排队
- `EXEC` 提交，一次性执行所有排队的命令
- `DISCARD` 取消事务
- `WATCH key` 在事务开启前监控 key，如果在 EXEC 之前 key 被改了，事务会被取消（乐观锁）

**局限性**：不支持回滚。如果 EXEC 中某一条命令出错，错误的跳过，其他的正常执行。

**在我的项目中**：没有用到事务。缓存操作都是简单的 `GET` / `SET` / `DELETE`，单个命令本身就是原子的。写操作（点赞、评论）的事务性由 MySQL InnoDB 保证，Redis 只负责失效缓存。

## 17. Redis 的 IO 多路复用是什么？

**传统 BIO（阻塞 IO）**：一个线程处理一个连接，如果连接上没有数据到来，线程就傻等，CPU 空转。10000 个连接 = 10000 个线程，线程切换开销巨大。

**IO 多路复用**：一个线程同时监听多个连接（文件描述符）。通过 `epoll`（Linux）系统调用，内核会告诉线程"哪些连接有数据到了"，线程只处理有数据的连接，其他连接不管。

**Redis 的模型**：
1. 一个主线程通过 `epoll` 监听所有客户端连接
2. 某个连接的请求数据到了 → 读取命令 → 解析 → 执行 → 返回结果
3. 处理完当前命令再去看下一个有数据的连接
4. 因为每个命令执行极快（微秒级），所以单线程也感觉不到排队

**在我的项目中**：Redis 这种模型意味着即使多个 Gunicorn worker 同时来取缓存，Redis 也能轻松处理，不会成为瓶颈。

## 18. 文件描述符（sockets 或者文件等）？

**文件描述符（File Descriptor，FD）** 是 Linux 内核用来标识"已打开资源"的一个非负整数。不只是文件，socket、管道、设备等一切 I/O 资源在内核层面都是 FD。

类比：图书馆的"取书号"。你要操作某个资源（读文件、发网络请求），系统给你一个号码，以后用这个号码来操作。

**在 Redis 的上下文**：每个客户端连接在 Linux 内核里都是一个 socket fd。Redis 默认最多同时持 10000 个 fd。通过 IO 多路复用，一个线程就能管理这 10000 个 fd。

---

## 19. 套接字（sockets）？

**Socket** 是网络通信的端点。"你的 IP:端口" 和 "对方的 IP:端口" 配对形成一个 socket 连接。类比打电话：电话号码 = IP:端口，通话 = socket 连接。

Socket 在 Linux 里也是一个文件描述符（FD）。Redis 客户端连接 Redis 服务器时，双方各自有一个 socket fd。数据从客户端 socket 发出，经过网络，到达服务器 socket，服务器读取处理。

## 20. I/O 资源是什么？

I/O 资源是指需要与外部设备交互的数据通道，在计算机里主要指：
- **磁盘 I/O**：读写硬盘（慢，毫秒级）
- **网络 I/O**：通过网络收发数据（包括 socket）

Redis 把核心数据放在内存，避免了磁盘 I/O。外部请求过来，处理的是网络 I/O + 内存读取，用 IO 多路复用让网络 I/O 不会成为瓶颈。这就是 Redis 快的底层原因。
